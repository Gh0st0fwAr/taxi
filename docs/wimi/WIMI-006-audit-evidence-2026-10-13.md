## 1. Канонический тариф WIMI

В WIMI-005 и WIMI-006 frontend-репозитория зафиксировано правило:

- €2,50 за каждый начатый 10-минутный блок (€15/час);
- неполный 10-минутный блок округляется вверх;
- минимальная длительность заказа — 120 минут;
- минимальная базовая сумма — €30;
- примеры: 120 мин = €30; 121/129/130 мин = €32,50; 131 мин = €35; 149/150 мин = €37,50; 151 мин = €40; 179/180 мин = €45.

В `taxi/src/wimi/mockAdapter.ts` локальная формула использует `Math.ceil(durationMinutes / 10)`. Это допустимо только для mock-тестов. В рабочей web-версии цену должен возвращать сервер.

## 2. Найденный серверный шаблон

В репозитории [BuevichRoman/MultiBot](https://github.com/BuevichRoman/MultiBot/blob/274cea96263d0b2d1baa442e76ff77ab1fb1772a/server/script_templates/nanny_pricing.php) есть шаблон `nanny_pricing`. Деплой-скрипт использует tenant `children` и API base:

`https://ibronevik.ru/taxi/c/children/api/v1`

Вызов шаблона: `POST /script/template/nanny_pricing`, поля `is_var=1`, `s_t_data` с JSON. Источник вызова в боте — `src/newManagers/api/APIManager.ts`, метод `pricingTemplate()`.

Поддерживаемые действия по исходнику:

- `quote`: принимает `when`, `time_zone`, `options`; возвращает `formula`, `price`, `options`, `calculationType`.
- `create`: принимает `request_key`, `time_zone`, `order`; записывает рассчитанный `pricingModel` и ключ в `b_options`; при совпадении ключа у того же клиента за последние 24 часа возвращает прежний `b_id` с `duplicate=true`.
- `final`: принимает `b_id` и необязательный `duration_min`; возвращает расчёт по сохранённой модели.

## 3. Критическое расхождение тарифа в проверенном исходнике

Исходник шаблона сам по себе пока не доказывает соблюдение WIMI-правила полных 10-минутных блоков:

1. `quote` жёстко устанавливает `duration = 0`; параметр длительности в его контракте отсутствует.
2. `create` вызывает `quote` без длительности, поэтому сохраняемая модель цены также получает `duration = 0`.
3. `final` передаёт `duration_min` в формулу как сырое число минут — округления вверх до 10 минут в шаблоне нет.
4. В проверенном шаблоне не найдено серверной проверки минимальной длительности 120 минут.
5. Повторный `request_key` возвращает найденный заказ без сравнения исходного payload. Это отличается от более строгого требования WIMI-006 о конфликте при том же ключе и изменённом payload.

Формула и константы читаются из `site_constants.pricingModels`, поэтому точную сумму в production нельзя подтвердить только по исходнику PHP. Реальный endpoint в этом аудите не вызывался; deployment SHA и фактические request/response не проверялись. До web-интеграции нужно согласовать/исправить серверную обработку длительности и подтвердить результат тестом на целевом tenant.

## 4. Блокеры web-интеграции

1. **Авторизация:** `MultiBot` вызывает шаблон с серверными admin `token/u_hash`. Эти credentials запрещено переносить в браузер. В web-форме WIMI нет входа и нет готового механизма получения пользовательских токенов. Нужно использовать пользовательские `token/u_hash` либо безопасный same-origin gateway.
2. **Контракт цены:** добавить/подтвердить duration-aware quote и округление/минимум на сервере; web не должен дублировать формулу.
3. **Создание:** шаблон ожидает `order` как payload `POST /drive`; WIMI draft сейчас содержит адрес строкой, но не содержит координат. Нужно подтвердить минимально обязательные поля backend и безопасное преобразование адреса.
4. **Идемпотентность:** создать один `request_key` на одно намерение заказа, переиспользовать его при retry и показывать возвращённый сервером `b_id`; не генерировать новый ключ автоматически после неопределённого timeout.
5. **Финализация:** `final` следует вызывать только для заказа, доступного текущему клиенту/няне; окончательная сумма должна отображаться из ответа сервера.
6. **Время:** использовать часовой пояс услуги и явное смещение для `when`; не интерпретировать локальное время браузера как время Малаги/Испании без преобразования.

## 6. Решение

Не включать реальное создание заказов из web, пока не подтверждены пользовательская авторизация, поля заказа/геокодирование и duration-aware серверный расчёт. Не использовать admin credentials в браузере и не заменять серверную цену локальной формулой. Следующий безопасный шаг — согласовать и исправить контракт `nanny_pricing` в отдельном PR, проверить его тестами, затем подключать web к тому же endpoint.
