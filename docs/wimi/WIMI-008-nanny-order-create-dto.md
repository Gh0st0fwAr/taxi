## Реализовано в WIMI

- `taxi/src/wimi/nannyOrderPayload.ts` — типизированное преобразование формы в `action=create`, проверка координат, длительности, числа детей и `request_key`, разбор ответа с `data.b_id`.
- `taxi/src/wimi/nannyOrderApi.ts` — вызов `POST /script/template/nanny_pricing` через пользовательский `apiMethod`. Административные `token/hash` не добавляются в браузерный запрос. Feature flag `REACT_APP_WIMI_ENABLE_REAL_CREATE` по умолчанию выключен.
- `taxi/src/wimi/nannyOrderPayload.test.ts` — тесты DTO, смещения Europe/Madrid, UTC-времени окончания, ответа сервера, валидации и отсутствия поля «Куда».

## Mapping

| WIMI | Серверный DTO |
|---|---|
| Координаты выбранного места услуги | `order.b_start_latitude`, `order.b_start_longitude` |
| Дата/время начала Europe/Madrid | `order.b_start_datetime` с явным смещением |
| Длительность | `order.b_options.b_end_datetime` в UTC |
| Количество детей | `order.b_passengers_count`, `order.b_options.childrenProfiles` |
| Идемпотентный ключ | `request_key`; шаблон записывает его как `b_options.requestKey` |
| Ответ | `data.b_id`, `data.duplicate`, `data.pricingModel` |

DTO не содержит адреса назначения, координат назначения или `to`: пользователь указывает только одно место оказания услуги. Комментарий формы не отправляется, потому что проверенный код бота не подтверждает поле для него. `b_comments` передаётся пустым массивом, так как WIMI не выбирает Taxi `booking_comments`.

## Плановая и фактическая стоимость

Это две разные суммы, и они не обязаны совпадать:

- **Плановая стоимость** рассчитывается сервером по приблизительным дате, времени и длительности, которые указывает заказчик. В DTO передаются плановые начало и окончание (`b_start_datetime` и `b_options.b_end_datetime`).
- **Минимальная длительность** — политика сервиса на сервере, а не поле DTO и не отдельное правило, которое фронт должен дублировать. Сервер применяет её при расчёте и возвращает результат; фронт отображает полученные от сервера цену и доступные сведения о расчёте.
- **Фактическая стоимость** рассчитывается после завершения услуги по реальному времени; серверный action `final` принимает `b_id` и `duration_min`. Отличие от плановой суммы допустимо.

Нельзя требовать, чтобы предварительная и финальная цены совпадали, и нельзя блокировать создание только потому, что фактическая длительность ещё неизвестна. Не добавлять минимальную длительность в DTO.

### Что остаётся проверить перед включением реального создания

1. Исправить и проверить серверный контракт предварительного расчёта: `quote` должен учитывать присланную заказчиком плановую длительность и применять минимальную длительность из серверной политики. Минимальная длительность не передаётся фронтом. Сейчас просмотренный `nanny_pricing.php` helper `quote` игнорирует `duration_min` и устанавливает `duration = 0`; `create` вызывает тот же helper, поэтому корректный расчёт по длительности пока не подтверждён.
2. На авторизованном тестовом пользователе проверить права на `create`, реальный ответ и повтор после таймаута.
3. Проверить, что повтор с тем же `request_key`, но изменённым содержимым не создаёт неоднозначный результат.
4. Прогнать контрактные тесты, DST и Taxi regression. Feature flag по умолчанию остаётся выключенным до завершения этих проверок.

**Состояние:** DTO/API-клиент подключены к UI за feature flag. По умолчанию flag выключен, поэтому UI остаётся в демо-режиме; реальные заказы не отправляются. Даже после включения flag серверный quote должен возвращать `calculationType=complete` прежде, чем пользователь сможет перейти к созданию.
