# WIMI-006 — Контракт backend и безопасный шлюз создания заказа

**Статус:** контракт `nanny_pricing` подтверждён по коду бота; серверный quote подключается в веб-ветке; реальный create пока заблокирован до проверки DTO и координат.  
**Зависимости:** WIMI-003 (обязательные блокеры), WIMI-005 (mock-first UI и регрессии).  
**Цель:** подготовить проверяемый контракт между WIMI UI и сервером, не открывая реальное создание заказов до выполнения требований безопасности и бизнес-правил.

## 1. Почему нужна эта задача

WIMI-004/005 обеспечивают пользовательский сценарий на mock-адаптере. Они не доказывают готовность backend и не должны считаться интеграцией с настоящими заказами.

В WIMI-003 зафиксированы неизвестные и блокеры:
- контракт шаблона подтверждён в `BuevichRoman/MultiBot`, commit `274cea96263d0b2d1baa442e76ff77ab1fb1772a`, файл `server/script_templates/nanny_pricing.php`; endpoint: `POST /api/v1/script/template/nanny_pricing` относительно API base tenant;
- административные `token/hash` используются существующим шаблонным API и не должны попадать в браузер;
- серверная цена и окончательная сумма авторитетны: веб-клиент не содержит локальную формулу тарифа;
- создание должно быть идемпотентным при повторе, таймауте и параллельных запросах;
- правила закрытия в полночь, начисления и чека должны исполняться сервером;
- часовой пояс места услуги и DST требуют серверной проверки;
- значение `b_passengers_count` и DTO детей/длительности нельзя выводить по догадке.

**Главный принцип:** сначала доказать контракт на коде и тестовом окружении, затем реализовывать интеграцию через безопасный серверный шлюз. Не подменять неизвестные ответы выдуманным API и не включать реальные заказы при невыполненных блокерах.

## 2. Результат WIMI-006

По завершении должны существовать:
1. Подтверждённая схема запросов и ответов с привязкой к конкретным серверным файлам/коммиту или документированному endpoint.
2. Подтверждённый пользовательский endpoint `nanny_pricing`; браузер передаёт пользовательские `token/u_hash` через существующий `apiMethod`, без административных credentials.
3. Типизированный frontend-контракт для preview/quote и create, отделённый от UI и mock-адаптера.
4. Сохранённый mock-режим по умолчанию и выключенный production create до прохождения release gates.
5. Контрактные тесты ошибок, авторизации, суммы, идемпотентности, времени и границ Taxi/WIMI.
6. Документ с фактическими результатами, оставшимися блокерами и SHA, на котором выполнены проверки.

Если канонический backend или тестовое окружение недоступны, задача останавливается на документированном audit gap. Не создавать фиктивный серверный контракт и не включать интеграцию.

6. Отдельно проверить, где и как сервер хранит время, начисления, финальную сумму и чек.

Не считать наличие функции, старого endpoint или ранее пройденных изолированных тестов доказательством корректности интеграции WIMI.

## 4. Контракт данных

Сначала составить документированную mapping-таблицу между полями WIMI draft, реальным backend DTO и сохраняемыми полями. Не добавлять поля в API только потому, что они есть в форме. В шаблоне `create` ожидает `order` по форме данных `POST /drive`; текущая форма WIMI не получает координаты адреса, поэтому реальный create ещё нельзя включать.

Минимальный логический набор входных данных для создания:
- адрес/подтверждённая локация услуги;
- локальная дата и время начала в часовом поясе места услуги;
- длительность;
- количество детей и возраст, если эти поля действительно поддерживаются backend;
- необязательный комментарий;
- ключ идемпотентности запроса.

Сервер должен самостоятельно определить/проверить:
- идентичность и право пользователя на создание заказа;
- канонический часовой пояс услуги и преобразование времени;
- тариф, минимальную длительность, eligibility и окончательную сумму;
- допустимость создания и итоговый статус.

Клиентская сумма — только предварительная подсказка. Клиент не может назначить окончательную цену, статус оплаты, статус назначения няни или результат закрытия заказа.

Для ответа создать типизированную схему после аудита фактического backend. Она должна различать:
- валидный quote/preview с breakdown и валютой;
- успешно созданный заказ с серверным ID, подтверждёнными датой/временем, длительностью, статусом и серверной суммой;
- конфликт повторного ключа с изменёнными данными;
- ошибку валидации с полевыми ошибками;
- отказ авторизации;
- временную/неопределённую ошибку, при которой результат create мог уже сохраниться;
- недоступность сервиса.

Не возвращать stack trace, внутренние сообщения SQL, секреты или административные данные.

## 5. Безопасный шлюз

1. Браузер WIMI обращается только к same-origin BFF или подтверждённому пользовательскому endpoint.
2. Административные `token/hash` для `nanny_pricing` остаются только на сервере. Их запрещено помещать в клиентский bundle, source maps, HTML, публичные конфиги, URL, browser storage, клиентские логи или ответы API.
3. Если существующий endpoint требует административные credentials, вызов выполняется сервер-сервер. Не обходить требование передачей admin credentials клиенту.
4. Сервер проверяет пользователя, права, типы и размеры входных данных, обязательные поля и бизнес-ограничения. Не доверять клиентской валидации.
5. Защитить endpoint от CSRF, если используются cookie-сессии; применить существующую модель auth и безопасные cookie/header-настройки.
6. Проверить CORS/preflight, если cross-origin доступ действительно нужен. Не добавлять `*` с credentials. Предпочесть same-origin BFF.
7. Логи должны содержать correlation/request ID, код результата и технически необходимую диагностику, но не токены, полный адрес, детские данные или содержимое секретных полей.
8. Существующий Taxi flow, API и Platform Core не должны менять поведение из-за WIMI-шлюза.

## 6. Идемпотентность создания

Ключ генерируется клиентом один раз для одного намерения создать заказ и повторно используется для всех retries этого намерения. Новый ключ создаётся только после явного начала новой заявки.

Backend обязан гарантировать:
- одинаковый ключ и одинаковый нормализованный payload возвращают тот же результат/ID, не создавая второй заказ;
- одинаковый ключ и существенно изменённый payload возвращают конфликт;
- конкурентные запросы с одинаковым ключом создают не более одного заказа;
- после таймаута или потерянного ответа повтор с тем же ключом позволяет узнать результат исходного запроса;
- поиск результата по ключу происходит до проверок, которые могли бы отклонить повторный запрос из-за уже созданного/занятого ресурса;
- определены срок хранения ключей, уникальность в БД и политика восстановления после частичного сбоя.

UI-защита от двойного клика из WIMI-005 не заменяет серверную идемпотентность.

Обязательные тесты: sequential retry, same-key/different-payload, два конкурентных create, timeout-after-commit/retry, сбой до commit и восстановление результата.

## 7. Канонические бизнес-правила

Сервер должен обеспечивать, а тесты — подтверждать:
- рабочее окно няни: 06:00–24:00;
- новые заказы принимаются до 22:00, но заказ обязан завершиться не позднее 00:00;
- минимальная длительность: 120 минут;
- цена: €2,50 за каждый **начатый** 10-минутный блок (€15/час); неполный блок округляется вверх;
- минимальная базовая сумма: €30;
- в 00:00 заказ автоматически закрывается, начисление прекращается и формируется чек;
- окончательная сумма и breakdown хранятся на сервере и доступны для аудита;
- оплата в текущем MVP — наличными няне; WIMI не должен имитировать онлайн-оплату.

### Обязательное разрешение противоречия тарифа

Каноническое правило для всех слоёв: если начался новый 10-минутный блок, он оплачивается целиком. Расчёт: ceil(длительность_минут / 10) × €2,50, при минимальной длительности 120 минут и минимальной базовой сумме €30,00. Примеры до дополнительных услуг: 120 минут = €30,00; 121 и 129 минут = €32,50 (оплачивается 130 минут); 130 минут = €32,50; 131 минута = €35,00 (140 оплачиваемых минут); 149 и 150 минут = €37,50; 151 минута = €40,00; 179 и 180 минут = €45,00. WIMI-005, UI preview, mock-адаптер и будущий backend обязаны использовать это правило и одинаковые граничные тесты.

## 8. Часовой пояс и DST

- Часовой пояс определяется на сервере по подтверждённой локации услуги и валидируется по IANA timezone.
- Не считать timezone из браузера или произвольный клиентский `time_zone` авторитетным.
- На транспортной границе хранить однозначный instant вместе с необходимыми локальными данными и идентификатором зоны для аудита.
- UI отображает время в часовом поясе места услуги.
- Обработать несуществующее и неоднозначное локальное время на переходах DST явной серверной ошибкой/политикой, не выбирать смещение молча.
- Тесты: `Europe/Madrid` для зимнего/летнего времени, перехода на летнее и обратно, даты с неоднозначным или отсутствующим временем, заказов около 06:00, 22:00 и полуночи.

## 9. Жизненный цикл, завершение и чек

До включения реальных заказов проверить и реализовать на сервере:
1. допустимые переходы статусов и защиту от повторного выполнения;
2. остановку начисления в 00:00 по часовому поясу услуги;
3. автоматическое закрытие даже если браузер пользователя закрыт или недоступен;
4. ровно одно логическое формирование чека при повторном запуске job/cron;
5. корректную обработку задержки cron и повторной доставки события;
6. сохранение final amount и billing breakdown;
7. отсутствие регрессии текущих Taxi заказов.

Не реализовывать полуночное закрытие в React как замену серверной задаче. Клиентский таймер не является источником истины.

## 10. Тестирование и безопасность

### Unit/contract
- DTO: валидные и некорректные поля, неизвестные поля, граничные длины.
- Quote: серверный ответ `nanny_pricing`; UI не дублирует тарифную формулу. Важно: `quote` не принимает длительность и возвращает предварительную сумму; `final` принимает `b_id` и опциональный `duration_min`, итоговую сумму рассчитывает сервер.
- Create: права доступа, повтор, конфликт ключа, конкурентные запросы, таймаут до/после сохранения.
- Time: рабочее окно, cutoff 22:00, конец в 00:00, конец после 00:00, IANA timezone, DST.
- Lifecycle: закрытие в полночь, прекращение начисления, идемпотентный чек.
- Errors: понятные безопасные коды ошибок без внутренних деталей.
- Regression: существующие Taxi API и order lifecycle.

### Integration/staging
- Запускать только на отдельном тестовом окружении и тестовых пользователях/данных.
- Убедиться, что повторный create не создаёт дубликат в реальной тестовой БД.
- Проверить, что секреты отсутствуют в production WIMI bundle и source maps, а browser network не содержит admin credentials.
- Проверить audit/logging и безопасное удаление тестовых заказов, если такая процедура существует.
- Полный Playwright E2E запускать только после проверки, что другой прогон с общими аккаунтами не активен. Сохранять `cancel-in-progress: false`; не отменять чужой активный прогон.

## 14. Результат проверки серверного тарифа (2026-10-13)

Источник: [MultiBot commit 274cea96263d0b2d1baa442e76ff77ab1fb1772a](https://github.com/BuevichRoman/MultiBot/commit/274cea96263d0b2d1baa442e76ff77ab1fb1772a), файл `server/script_templates/nanny_pricing.php`.

| Action | Подтверждённое поведение | Статус веб-версии |
|---|---|---|
| `quote` | Рассчитывает предварительную цену по серверной модели и выбранным опциям | Подключается этим изменением |
| `create` | Создаёт заказ с серверной `pricingModel`; повтор с тем же `request_key` в течение суток возвращает прежний `b_id` | Пока не включён: адресная форма не даёт координат и mapping DTO не подтверждён |
| `final` | Возвращает итог по заказу; `duration_min` позволяет запросить цену за указанную длительность | Пока не подключён к веб-сценарию, поскольку веб-сценарий создаёт только локальную демо-запись |

Форма веб-версии использует `Europe/Madrid` как часовой пояс услуги и отправляет дату/время с корректным сезонным смещением. WIMI build выбирает tenant `children` только в памяти процесса, не перезаписывая общий `localStorage.config`, и пытается восстановить существующую авторизованную сессию. UI не содержит экрана входа: без сохранённого пользовательского токена quote блокируется и показывает сообщение о необходимости войти в аккаунт. Это допущение соответствует текущему Spain MVP; при поддержке других стран часовой пояс должен определяться по подтверждённой локации.

Реальное создание заказа остаётся выключенным. Перед его подключением необходимо подтвердить ответ deployed endpoint на авторизованном тестовом пользователе, обязательные поля `order`, координаты/геокодирование, правила адреса и безопасное восстановление результата после таймаута. Не передавать admin token/hash в браузер.
